How to sign your release

For authors: five minutes, once

Let GitHub build your firmware from your source and sign it. Then everyone can check that the .fwsc they install is exactly what your code builds, and your card on the hub gets the key Built from source on GitHub. You need nothing but your repository: the hub's shared build workflow zvenson/fm1-build does the toolchain, the build, the signature and the release.

  1. Add one file to your repository: .github/workflows/release.yml 
    name: release
on:
  push:
    tags: ["v*"]
jobs:
  build:
    uses: zvenson/fm1-build/.github/workflows/build.yml@v1
    permissions:
      contents: write        # the release
      id-token: write        # the signing certificate
      attestations: write    # the attestation
    with:
      build: ./build.sh --release "${GITHUB_REF_NAME#v}"   # your build command
      packages: build/*.fwsc                                # the package(s) it makes
      # test: sh tests/run_tests.sh                       # optional
    Change only the two lines build and packages to your project's build command and where it puts the .fwsc. The JieLi toolchain is there ($JIELI_TOOLCHAIN), the AC79 SDK too ($AC79_SDK). With a test line, a failing test stops the release.
  2. Push a version tag: git tag v1.2 && git push origin v1.2
  3. Watch it run in your repository's Actions tab (about two minutes). Green: your release is there, with the signed .fwsc attached. Do not replace or add the file by hand afterwards.
  4. On the hub: the next sync (every three hours) takes the release, checks the signature and shows the key on your card, linked to the commit and the build log.
  5. Check it yourself (or let your users): 
    gh attestation verify myfw-1.2.fwsc --repo you/myfw \
  --signer-workflow zvenson/fm1-build/.github/workflows/build.yml

If it does not work: the build must run on GitHub's Ubuntu runner, so a step that only works on your computer fails there (look at the log in the Actions tab). The three permissions lines are needed. The hub only trusts @v1 of the shared workflow, a package built by your own workflow does not get the key. A file uploaded or rebuilt by hand after the run does not either: the hub compares its SHA-256 with the signed one. Questions: an issue on fm1-build or the FM-1 Discord.

What the key means, and what it does not: Built from source on GitHub.

The package: a .fwsc file

For everyone

Every FM-1 firmware comes as one file ending in .fwsc. It is the format of M-VAVE's own updater, and every custom firmware uses it too. Inside are two programs: the update loader, a small helper that writes the firmware, and the firmware itself, the instrument you play.

The first bytes of the file also carry the package's identity, a short name such as FM-1_015. The official firmware V15 is FM-1_015. Custom firmwares pick their own.

The identity: which firmware is this?

For everyone, and important for authors

A running FM-1 answers over USB with the identity of the firmware it runs. The hub uses that answer for one thing only: after you press Connect FM-1, the card of the firmware on your FM-1 gets the mark on your FM-1.

Many firmwares are built on Felucca, SLOOP or X0X, and several of them keep the number of the project they started from. Then two or more firmwares answer with the same identity, and the hub cannot know which of them is on your FM-1.

A shared identity breaks nothing. Installing, updating and going back work exactly the same. The only difference: the hub does not mark any card as on your FM-1 when more than one firmware fits. It says which identity it sees, and you know which one you installed.

For authors: please give your firmware its own number

Pick an identity no other firmware uses. The table below shows every identity on the hub right now. A number that also encodes your version works well, as Charles Vestal's firmwares do: FM-1_9010003 is X0X 1.0.3. Keep the part before the version yours, so that no other project can collide with it. Change it in your build, release, and tell us: your card then gets an exact check and the on your FM-1 mark.

The update loader

For everyone

The FM-1 cannot overwrite the program it is running. So an update happens in two steps: the running firmware first starts the update loader from the new package, and the loader then writes the new firmware. The loader comes from the new package, so every package brings its own.

Felucca's loader

Almost every custom firmware uses the loader from Felucca by Hügelton Instruments. While it waits in update mode, the loader reports the new package's identity. For identities of the form FM-1_9NN, the hub picks up an interrupted update: plug the cable back in, press Install again, and it continues where it stopped.

M-VAVE's own loader

The official V15 brings M-VAVE's loader. A firmware can also be built on top of the official V15 with only the instrument replaced, as Bubba Machine is. Then it brings M-VAVE's loader too. The hub installs it the same way it installs V15 itself, and it can resume an interrupted update of that firmware as well.

An update stopped halfway? The FM-1 stays in update mode and waits. Plug it in again and press Install on the same card. If the hub says the FM-1 is in another firmware's update mode, finish that update with that firmware's own installer, or use the USB rescue described below.

What happens when you press Install

For everyone

CheckedThe page loads the package from the hub and compares it with the catalogue: identity and SHA-256 fingerprint.
LoaderThe running firmware reads the package over USB MIDI and starts the new update loader. The FM-1 restarts.
WrittenThe loader writes the firmware, the FM-1 restarts again and reports its new identity.

All of this runs in your browser, over Web MIDI, which only Chrome and Edge have. Nothing is sent to a server. It takes about a minute. Do not unplug while it says Writing.

What the hub checks, and what it does not

For everyone

The hub looks at every listed project's GitHub repository several times a day and takes its newest release. Before a package is offered, it must pass these checks:

  • It is an FM-1 package. Its identity starts with FM-1_ and matches what the project reports.
  • It has its update loader. Felucca's loader, or M-VAVE's own for a firmware built on the official V15.
  • It is unchanged. The hub mirrors the file byte for byte and pins its SHA-256 fingerprint. Your browser checks that fingerprint again before it writes anything.

Two more facts are read from every package and shown on its card when they hold: whether GitHub built it from its source, and whether it can act as a USB keyboard or mouse. They inform, they do not judge.

A release that fails a check is not offered. The last good one stays on the card. If a repository disappears, its card leaves the hub and comes back when the repository does.

What the hub does not check: whether a firmware works well, sounds good or keeps your data. The hub does not test the firmwares of other authors. Questions and bug reports go to each project, linked on its card.

Betas

A card says beta when the version is below 1.0 or its name says beta, alpha, rc or test. A beta may change how it saves your work from one release to the next.

Why the hub mirrors the files

A browser is not allowed to download a release file from GitHub directly. So the hub keeps a copy of each package, and a copy of its source code next to it. The firmwares are open source under the GPL-3.0, which allows passing them on unchanged with their source.

Built from source on GitHub

For everyone, and how authors get it

A .fwsc is a compiled file. Anyone can read a project's source code, but nothing in the file itself shows that it was built from that code. Some projects let GitHub build their release instead of a computer at home, and GitHub then signs a statement: this exact file (its SHA-256 fingerprint) was built by this workflow from this commit. That signed statement is an artifact attestation.

The hub looks for one for every package it offers and checks it properly: the signature, Sigstore's certificate and public transparency log, that the file is the one the hub serves, that it was built from the project's own repository for a release tag, and that it was built by the hub's shared build workflow. When all of that holds, the card gets the grey key Built from source on GitHub, which opens the exact commit.

Why a shared workflow: a project's own workflow can download anything during the build and put it into the file, and GitHub would still sign it. One build workflow for everybody, published and reviewed once, only checks out the tagged source and runs the project's build. So the signature means what it says.

What it does not say: that the firmware is safe or good. It says where the file came from, so that what you read in the source is what you install. Whether the code does what it should is up to those who read it. The hub does not review the firmwares' code.

For authors: get the key

Step by step at the top of this page: How to sign your release. The shared workflow is zvenson/fm1-build: one short file, every action pinned, open for review. Changes come as new tags, never by moving one.

  • The hub checks the release asset's SHA-256: the file the workflow attested is the file on the release. A file changed, rebuilt or uploaded by hand afterwards does not get the key.
  • Your build has to run on GitHub's Ubuntu runner with what it can install there (the toolchain from its download, for example).
  • Check it yourself with gh attestation verify myfw-1.2.fwsc --repo you/myfw --signer-workflow zvenson/fm1-build/.github/workflows/build.yml.
  • The hub checks each new package once. Releases without an attestation stay on the hub exactly as before.

“Can act as a USB keyboard / mouse”

For everyone

Over USB the FM-1 normally shows up as a MIDI device (and with some firmwares as an audio device). A firmware can also tell the computer that it is a keyboard or a mouse: then it can type and move the pointer like one. That is how macro pads and many controllers work, and it is a fair reason for a firmware to do it.

It is also worth knowing, because a device that types can type anything. The hub reads every package it offers, opened as the FM-1's own update reads it, and looks for the USB descriptors of a keyboard or a mouse. When it finds one, the card gets the amber key and a line saying so.

This is a fact about the file, not a verdict. The hub does not know what a firmware types, or when, and does not review its code. No key does not prove a firmware can not do it either: only that the hub found no keyboard or mouse in it.

Try it before you install

For everyone, and for authors

In the browser

Many firmwares have their own simulator: the firmware's sources built for the browser, with its screen and its sound. On the hub their cards say ▶ Play in the browser. Nothing is installed, and nothing touches your FM-1. OberVave's, for one, is its unchanged firmware: the same sound and screens as on the device, with the computer keyboard or a MIDI keyboard.

The real package, on your computer

fm1-emulator by Simon Johansson emulates the FM-1 itself: its chip (pi32v2) and its board, built on QEMU (GPL-2.0). It runs the same .fwsc you would install, with the screen, the keys, the knobs, the LEDs and the sound, and the firmware's console in your terminal. Download it from its releases (macOS on Apple Silicon, Linux on x86-64; Windows not yet), then:

./emulator felucca-1.5.fwsc

It takes an uncompressed .fwsc or .ufw package or a raw application .bin. Click the keys and buttons, drag or scroll the knobs; on the keyboard Z…C play notes, X / V change the octave, P / O are ENV / LFO, H goes HOME. A firmware's package is linked on its card (release), and the hub keeps a copy of each next to the page.

Confirmed by its author: the official V15 and Felucca. Most firmwares on the hub boot in it; a few still stop at an instruction or a chip part the emulator does not have yet (in our tests AMB-1, TRIBE, Bubba Machine, DUELL and FM-106). Its browser build is experimental and still far slower than real time.

More emulators, among them fm1-emu by Joakim Eriksson in the browser, editors and backup tools: Tools.

For authors: boot your release in it before you publish. It catches a package that does not start before anyone's FM-1 does, and it is how the hub's videos are recorded: unchanged packages, real screens, real sound.

Your projects, presets and samples

For everyone

All firmwares keep what you make in the same flash memory of the FM-1, and each in its own way. After a switch, the new firmware may not read what the old one saved. It may start empty, or it may overwrite parts of it.

  1. Back up first. Use the backup of the firmware you are on. Each project's page says how.
  2. Then switch. Firmwares from the same family, such as Felucca and its forks, often read each other's projects. Others do not.
  3. Coming back to a firmware does not always bring your old work back. Restore it from your backup.

Back to the official firmware

For everyone

Press Back to official V15 in the Official firmware box on the hub. It installs M-VAVE's own FM-1 V15, the recovery image M-VAVE publishes in m-vave/fm1_open under the Apache-2.0. The hub serves it unchanged with M-VAVE's licence and notice, and your browser checks every byte (its SHA-256) before it writes. You can also download V15 from m-vave.com/download (PC Firmware, FM-1) and choose the file in the same box: only that exact file is accepted.

The USB rescue

Step by step, by what you see: FM-1 rescue. Charge the FM-1 fully first, and if a step does not help, stop and write to us before you try the next tool.

Saves gone after power-off, or every update fails? A newer FM-1 with the flash chip 0xB36014 and a firmware that knows only the first units' 0x856014: it does not write the flash. The rescue page lists the firmwares that know both and shows how to put one on, from Windows, Mac or Linux.

If the FM-1 does not start any more, hold OCT− while you switch it on. It then waits for an update over USB. Connect it and install any firmware, or V15, from the hub.

If no installer finds it and the computer only sees a USB disk "WL82 UBOOT1.00", the chip's bootloader in ROM still answers, and no update can erase it. M-Flasher (Windows, macOS, Linux, MIT), MvaveFM1Unbricker by Quixotic7 (Windows and Linux, MIT) and the hub's Rescue (Linux) put a firmware back through it; M-Flasher and the Unbricker keep a full backup of the flash first. An FM-1 that never shows that disk can come back with the FM-1 Transporter, a small RP2040 board on the USB lines (step by step).

Getting your firmware listed

For authors

The hub lists a firmware when all of this is true:

  • It makes music. Synths, grooveboxes, drum machines, samplers, chord instruments, controllers. Games and tools without sound are not listed.
  • It is open source, with its source code public in the repository and a license that allows passing it on, such as the GPL-3.0.
  • It has a .fwsc on a GitHub release. The hub checks the releases on its own several times a day, so every new release appears without anyone doing anything. A project without releases can name its package in a web installer instead. If your release has more than one .fwsc, tell us which one is the firmware.
  • The package has an update loader and an identity starting with FM-1_. See the identity section for why your own number helps.

Optional, and recommended: let GitHub build the release and attest it, so the card can show Built from source on GitHub. How to sign your release: five minutes, once. You can write your card's text yourself, too: fmhub.json.

Before you send it: test it as a player will use it

This is the most important part. The hub runs no tests of its own: you are the only one who tests your firmware. Players press Install trusting that it works. A firmware that installs but does not start the next update leaves them with an FM-1 they cannot change any more, and most of them will not know how to get out. Please do every check below on a real FM-1, with the very file from your release, before you mail us. Untested firmwares are not listed; a listed one that breaks this is taken off until it is fixed.

  • Install it from the official V15 and from another custom firmware. Both must end with your firmware running and the hub naming it after Connect.
  • Leave it again. With your firmware running, install another one. Your firmware must start the next package's update loader when asked (see What happens when you press Install). If it does not, players can only get away by holding OCT− at power-on, and most of them will not know that.
  • USB. The FM-1 shows up as a MIDI device, answers the identity request with your own FM-1_ number, and its port name is one the hub knows (FM-1, or your firmware's name: tell us).
  • An interrupted update. Unplug during Writing once, plug in again and press Install: the update should continue (which loaders allow it: the update loader).
  • Projects and samples. If your firmware cannot read what another one saved, or overwrites it, say so in the README: the hub tells players to back up first, your README tells them why.

Mail zven@thefirmwarehub.com with the name, the repository and a sentence about what it does. A picture of its screen helps: the cards show each project's real screen, taken from its repository.

Not ready yet?

A firmware without a release package can not be listed yet. Attach the .fwsc to a release, and it can go on the hub the same day. Closed-source firmwares are not mirrored. A very popular one may get a link card that sends you to its maker's own installer.

Your card's text, from your repository

For authors: required for new firmwares

You write your card's text. Put a file named fmhub.json in the root of your repository, on its default branch. New firmwares are only listed with it.

{
  "what": "A six-track groovebox: TR drums, a sampler with a mic input, a step sequencer and song mode.",
  "author": "Your Name",
  "kinds": ["groove"],
  "play": "https://you.github.io/myfw/play/",
  "editor": "https://you.github.io/myfw/editor/",
  "cheat": "https://you.github.io/myfw/cheatsheet.pdf",
  "image": "docs/card.png",
  "color": "#FF7A00"
}
  • what: the card's text, in English. Plain words: no HTML, no code, no links or web addresses. Up to 300 characters: a longer text is cut at a word. Say what it is and what you can do with it. Write about this version, not your plans.
  • author: optional, your name as the card shows it under the title (otherwise the one we wrote down when your firmware came on the hub). Plain text, 2 to 60 characters, no links.
  • kinds: one of synth, groove (groovebox), drums (drums and samplers), chords, tracker and other (more than one: the first counts). It is the filter above the cards; pick the one people would look under.
  • play: optional, your firmware running in the browser (the card's green ▶ key). An https:// address.
  • editor: optional, your web editor for its sounds or settings (the card's pink key). An https:// address.
  • cheat: optional, your cheat sheet (the card's sheet key): an https:// address of a web page or a PDF, for example on your GitHub Pages.
  • image: optional, your card's picture: the path of a file in your repository, e.g. docs/card.png. Square, 240 × 240 to 1024 × 1024 pixels, PNG, WebP or JPEG, 300 KB at most. Best: a capture of the FM-1's screen at 240 × 240 as PNG (a few KB, pixel-sharp), or a photo as WebP. The hub copies it and serves it itself; replace the file, keep the path, and the card follows within three hours.
  • color: optional, your card's colour line (under the picture) as #RRGGBB, e.g. #FF7A00. Bright enough to be seen on the dark page; a very dark one is refused.

Changing it: edit the file and push. The hub reads it every three hours and your card shows the new text by itself, no mail. No advertising and nothing hostile against anyone: such a text is refused, and we read every new text that goes on a card. A file that breaks this is taken off the card for good. Under its text every card says where the text comes from, and if your file has a mistake, the card says which. The firmware's name and version always come from your repository and your releases, not from this file.

Using an AI assistant? Give it fmhub.md: everything it needs to write this file, the picture and the rest of a listing for you.

Using the hub's firmware list

For app and tool makers

The hub's list of firmwares is open for your app, store, installer or tool: catalog.json (name, maker, text, picture, version, release, sha256, identity, flash chip, update loader – only firmwares that passed the hub's checks). Its compilation – the selection, the checks, identities, chips, loaders and versions – is licensed under CC BY 4.0.

  1. Name the hub, with its address: “Firmware list: The Firmware Hub – thefirmwarehub.com”. Where links work (a web page, an app with a browser) as a working link to https://thefirmwarehub.com; on a device without a browser the address written out – once where people see it, e.g. the list's title or info screen and its About, not all the time. Plus the licence and whether you changed anything.
  2. The makers' texts and pictures are theirs (from their fmhub.json and their repositories), not the hub's and not under this licence: name each firmware's maker and link its repository.
  3. Read catalog.json at most once a day, with a User-Agent that says who you are. Don't read the pages, and download the packages from the makers' releases, not from the hub.
  4. Keep players safe: install only a package whose sha256 matches the list, never one marked "chip": "old" on an FM-1 with the newer flash chip, and drop what drops out of the list.
